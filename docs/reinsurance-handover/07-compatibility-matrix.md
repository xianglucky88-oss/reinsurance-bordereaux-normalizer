# 07 · 兼容矩阵

> rule_version `R-809d7c1.1` · 每一种反应均由样例或实跑验证，非推测

本矩阵回答四个问题：经纪人模板升级、treaty 生效、汇率修订、回滚，各自在当前实现下会发生什么。

图例：

- ✅ 兼容，无需改造
- ⚠️ 可运行但语义可疑（会静默出错）
- ❌ 不兼容，运行失败
- 🚫 引擎无此能力（业务未实现）

---

## A. 经纪人模板升级

对每一种常见模板改动，实测引擎反应如下。

| # | 模板改动 | 引擎反应 | 判定 | 证据 |
| --- | --- | --- | --- | --- |
| A1 | 增加新列（如 `ceded_pct`、`broker_ref`） | 忽略，结果不变 | ✅ | 实跑验证 |
| A2 | 重命名 `currency` → `ccy` | 忽略，结果不变 | ✅ | F07 变体实跑 |
| A3 | 删除 `currency` | 忽略，结果不变 | ✅ | 实跑验证 |
| A4 | 重命名 `amount` → `gross_paid` | `KeyError: 'amount'` | ❌ | 实跑验证 |
| A5 | `amount` 改为字符串 `"50.00"` | 静默强转为 50.0 | ⚠️ | F13 |
| A6 | `amount` 含千分位 `"1,200"` | `ValueError: could not convert` | ❌ | E04 同类 |
| A7 | 重命名 `claim` → `claim_ref` | `KeyError: 'claim'` | ❌ | 实跑验证 |
| A8 | 重命名 `movement` → `txn` | `KeyError: 'movement'` | ❌ | 实跑验证 |
| A9 | 重命名 treaty `name` → `layer` | `KeyError: 'name'` | ❌ | 实跑验证 |
| A10 | 重命名 treaty `limit` → `top` | `KeyError: 'limit'` | ❌ | 实跑验证 |
| A11 | 同时提供 `limit` 和 `top` | 只读 `limit`，`top` 被忽略 | ⚠️ | 实跑验证 |
| A12 | `limit` 语义由"层宽"改为"层顶" | 层宽变 `top - attachment`，静默错算 | ⚠️🔴 | 见 §A.1 |
| A13 | `attachment`/`limit` 改为字符串 | `TypeError`，整次运行失败 | ❌ | E02 |
| A14 | `attachment`/`limit` 改为小数 | 接受，按浮点计算 | ⚠️ | 实跑验证 |
| A15 | `amount` 嵌套为 `{paid: 50}` | `KeyError: 'amount'` | ❌ | 实跑验证 |
| A16 | 列顺序改变 | 不影响（按 key 取值） | ✅ | — |
| A17 | 行顺序改变 | **改变分摊结果** | 🔴 | F03a/F03b |
| A18 | 新增外币列但不做换算 | 无反应；不同币种金额仍直接相加 | 🚫 | F07 |

### A.1 A12 为什么是最高风险项

若 broker 模板把原来表示"层宽"的列改叫 `top`，或把 `top` 的值填进 `limit`：
- 引擎仍能跑，不报错。
- 层区间变成 `[attachment, attachment + top]`，比真实区间宽。
- 结果 `status: ok`，但分摊系统性偏高。

**在"模板改动"这一类里，A12 是唯一不报错、语义错、且难以察觉的项。** 审查时必须逐字段核对 `limit` 的口径。（A17 行序敏感属于数据提交问题，不是模板列语义问题。）

### A.2 模板升级的安全路径

| 步骤 | 动作 |
| --- | --- |
| 1 | 用新模板样本跑 `python3 tools/trace_allocation.py <新样本>`，确认源列映射命中 |
| 2 | 若列被重命名，**在 loader 层做映射**，输出归一化 `{claim, movement, amount, currency}` + `{name, attachment, limit}`，引擎不改 |
| 3 | 跑 `python3 tools/check_samples.py` 确认 28 样例未漂移 |
| 4 | 对 A12 类语义变更，单独构造对照样本，人工比对区间 |

## B. Treaty 生效

| # | 场景 | 引擎反应 | 判定 | 证据 |
| --- | --- | --- | --- | --- |
| B1 | 新增一层 | 按 attachment 插入排序，参与分摊 | ✅ | 实跑验证 |
| B2 | 删除一层 | 该层消失，损失重新分配 | ✅ | — |
| B3 | 修改某层 limit | 整次运行按新值重算，**历史 movement 被重述** | 🔴 | F15、F20 |
| B4 | 新增 treaty 版本并将 `effective_from` 写入 | 字段被忽略，无生效日概念 | 🚫 | 登记册 `not-representable` |
| B5 | 只让新版本作用于某月之后 | 不支持；一次运行一个数组 | 🚫 | F15 |
| B6 | 层重叠 | 重复计算，静默 | 🔴 | F04 |
| B7 | 层间缺口 | 损失落入 unallocated，静默 | ⚠️ | F05 |
| B8 | 两层 attachment 相同 | 按输入顺序，无优先规则 | ⚠️ | F14 |
| B9 | 负 attachment | 接受，产生反常区间 | ⚠️ | 实跑验证 |
| B10 | limit = 0 或负数 | 空区间，静默无分摊 | ⚠️ | 实跑验证 |
| B11 | 输出需要版本标签 | 不含 version | 🚫 | 02 节已证 |

### B.1 Treaty 生效的操作建议

| 路径 | 可行性 | 说明 |
| --- | --- | --- |
| A. 全历史 + 新版本 | ✅ 能跑 | 历史被重述；必须留存输入的旧版本以支持回滚 |
| B. 按生效日拆分 movement，分批运行 | ✅ 能跑 | 拆分在 loader 完成；会切断累计（F11b 风险） |
| C. 引擎内部版本化 | ❌ 不支持 | 需要改代码（新增 effective 字段 + 期间累计） |

> 无论选 A 还是 B，**都必须同时记录 `registers/treaty_change_register.json` 的 `change_log`**，否则下次维护者无法知道历史结果是在哪个版本下算出的。

## C. 汇率修订

| # | 场景 | 引擎反应 | 判定 | 证据 |
| --- | --- | --- | --- | --- |
| C1 | 输入含 `fx_rate` 列 | 被忽略，不参与计算 | 🚫 | F07 |
| C2 | 多币种直接提交 | 数字按 1:1 相加 | 🔴 | F07 |
| C3 | 修改汇率后希望重算 | 引擎无汇率概念，改输入金额才能影响结果 | 🚫 | — |
| C4 | 输出需带汇率/币种 | 不含 | 🚫 | 02 节 |
| C5 | 按汇率日区分 | 无日期字段 | 🚫 | NI-LOSS-DATE |
| C6 | 金额为数值字符串 | 静默强转 | ⚠️ | F13 |
| C7 | 金额精度超过 2 位 | `round(...,2)` 截断，half-to-even | ⚠️ | F08a/F08b |
| C8 | 大量小于 1 分的 movement | 逐段舍入漂移，累计与明细不等 | 🔴 | F09、F17 |

### C.1 汇率修订的正确前置

由于引擎无汇率能力，汇率换算**必须在输入前完成**：

```
原始 bordereaux（多币种）
   │  ← 在 loader 层按 rate_date 取汇率，换算为 treaty 币种
   ▼
单币种、2 位小数、已舍入的 amount
   │
   ▼
引擎（只做累加与分层）
```

若跳过前置：
- 结果不可审计（输出无币种/汇率）。
- 汇率修订无法表达为"变更"，只能表现为"输入金额不同"，历史无法追溯。
- F17 说明：即便单币种，大量小额也会因逐段舍入产生 0.90 的漂移；多币种换算会放大该效应。

## D. 回滚

| # | 回滚对象 | 手段 | 是否可行 | 说明 |
| --- | --- | --- | --- | --- |
| D1 | treaty 定义 | 恢复旧 `treaties` 数组，重跑 | ✅ | F21 为 v1 基线 |
| D2 | 规则版本 | 切回旧 commit + 旧 manifest | ✅ | 源文件哈希记录在 manifest |
| D3 | 经纪人模板 | loader 映射回旧列名 | ✅ | 引擎不改 |
| D4 | 已发出的输出 | 仅凭输出回退 | ❌ | 输出无版本/期间标签，新旧不可区分 |
| D5 | 已入账的财务结果 | 下游冲正 | ❌（引擎侧） | 需下游配合 |
| D6 | 汇率修订 | 恢复旧汇率并重算 | ⚠️ | 需重跑输入换算；引擎无汇率记录 |
| D7 | 重复提交造成的翻倍 | 删除重复行 + 重跑 | ⚠️ | 引擎不识别重复，必须人工/上游定位（F19） |

### D.1 回滚证据链（唯一可靠方式）

```
每次运行必须同时留存：
  1. 输入文件（原始 bordereaux）
  2. rule_version + commit sha
  3. samples/manifest.json 中的 engine.files_sha256
  4. 本次运行的输出 JSON
```

缺任何一项，回滚后都无法证明"这次结果与上次结果同源"。

## E. 一页速查

| 变更 | 需要改引擎吗 | 是否需要重跑历史 | 静默风险 |
| --- | --- | --- | --- |
| 经纪人增加列 | 否 | 否 | 低 |
| 经纪人改 `currency` | 否 | 否 | 无（但币种仍不换算） |
| 经纪人改 `amount`/`claim`/`movement` 名 | **需 loader 映射** | 否 | 中（否则 KeyError） |
| 经纪人改 `limit` 语义 | 否 | 是 | **高（A12）** |
| 新增/删除层 | 否 | 是 | 中（重叠/缺口） |
| 修改层 limit | 否 | 是 | **高（重述历史，F20）** |
| treaty 按生效日生效 | **是** | 是 | 高（不支持的模型） |
| 汇率修订 | **是**（或前置换算） | 是 | 高（无币种概念） |
| 更正历史 movement | 否 | 是 | 高（F03a/F03b 顺序敏感） |
| 重投整份文件 | 否 | 是 | **高（F19 累计翻倍且无告警）** |
