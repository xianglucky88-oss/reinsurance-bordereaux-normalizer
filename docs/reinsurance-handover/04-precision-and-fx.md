# 04 · 跨币种与跨精度

> rule_version `R-809d7c1.1` · 样例 F07–F09、F13、F17

## 1. 跨币种：引擎没有币种概念

### 证据 F07

输入：`C1/M1 = 120 USD`、`C1/M2 = 80 EUR`；层 `L1 = 100 xs 500`。

引擎输出：

| 行 | amount（原样） | 参与累加的值 |
| --- | --- | --- |
| C1/M1 | 120 USD | 120 |
| C1/M2 | 80 EUR | 80 |

`cumulative_loss = 200.0`。

这 200 **没有币种**。它既不是 200 USD，也不是 200 EUR。

### 为什么这是硬缺口

- `currency` 在 `src/` 中零引用（`grep -rniw currency src/` → 0）。
- 输出信封不含 `currency`，也不含任何汇率字段。
- 因此下游拿到 `allocated: 80.0` 时，**无法知道**它是以什么币种计价、由什么汇率得来。

### 未实现清单（汇率）

| 需要的能力 | 状态 | 说明 |
| --- | --- | --- |
| 汇率表 / 汇率日 | NOT IMPLEMENTED | 无 `fx_rate`、`rate_date` 读取 |
| 结算币种转换 | NOT IMPLEMENTED | 无转换，直接相加 |
| 分币种累计 | NOT IMPLEMENTED | 只有一条全局 `cumulative` |
| 汇率对输出可追溯 | NOT IMPLEMENTED | allocation 行不带币种/汇率/汇率日 |

> 交接结论：**任何多币种 bordereaux 在当前实现下产出的都只是"无单位数字之和"**，不可直接用于财务入账或 treaty 结算。必须在上游统一换算为单一币种后再输入，或改造引擎。

## 2. 跨精度：`round(x, 2)` 的真实语义

引擎用 `round(..., 2)`（engine.py:8）。需要注意三点。

### 2.1 是 half-to-even，不是四舍五入

| 输入 | 输出 | 说明 |
| --- | --- | --- |
| 0.125 | **0.12** | 向偶数舍入（2 是偶数） |
| 0.135 | **0.14** | 向偶数舍入（4 是偶数） |
| 2.675 | **2.67** | 二进制表示偏小导致向下 |

样例：F08a、F08b。

业务上若要求 half-up（四舍五入），`round()` **不符合**。差异虽小，但在大额或大量 bordereaux 上会累积成对账差异。

### 2.2 逐 movement 舍入不满足望远镜求和

由于每条 movement 各自 `round`，`Σ round(Δᵢ)` 通常不等于 `round(Σ Δᵢ)`。

| 场景 | cumulative | Σ allocated | 差 |
| --- | --- | --- | --- |
| 2 × 0.005 | 0.01 | 0.02 | **+0.01** |
| 2 × 0.015 | 0.03 | 0.02 | -0.01 |
| 2 × 1.005 | 2.01 | 2.00 | -0.01 |
| 200 × 0.005（F17） | 1.0000000000000007 | 1.9000000000000015 | **+0.90** |

F17 是最直观的证据：200 条 0.005 的 movement，每条被独立 `round(...,2)` 到 0.01（`0.005` 的二进制值实际为 `0.005000000000000000104…`，略大于十进制 0.005，故在 2 位小数处向上进到 0.01），累计却只有约 1.0。**分摊合计几乎是累计的两倍。**

需要区分两种机制：

- **half-to-even 真正起作用**只发生在值在二进制下可精确表示为中点时，如 `0.125`、`0.375`（F08a/F08b）。
- 像 `0.005` 这类十进制中点无法精确表示，二进制漂移主导结果：`0.005` 实际偏大，故 2 位小数处向上进到 0.01。

两者都是 `round()` 的正常语义，但都不是业务人员口中的"四舍五入"。

### 2.3 小于半分钱的 movement 完全消失（F09）

两条 0.004：各自 `round(0.004, 2) = 0.0`，`if amount` 为假，**不产生任何 allocation 行**。但 `cumulative_loss` 仍记录 0.008。

因此：

- 明细行合计 ≠ cumulative（差 0.008）。
- 这 0.008 落进 `unallocated`，却不对应任何真实"未分摊损失"。

## 3. 浮点表示的噪声（F08a）

`0.125` 分摊保留为 0.12 后，`unallocated = 0.0050000000000000044`——一个带浮点尾差的数。

原因：`cumulative` 是浮点累加（engine.py:4），`unallocated = max(0, cumulative - sum)`（engine.py:10）未做舍入。

**含义**：任何直接按 `unallocated == 0.0` 做断言的后处理都会在正常数据上误报。

## 4. 数值字符串（F13）

`amount: "120"` 被 `float()` 静默接受为 120.0。这本身方便，但意味着：

- **无法区分**"经纪人漏填 amount 但填了字符串"与"经纪人正确填写了数值"。
- 若字符串含千分位（`"1,200"`）或货币符号（`"USD 120"`），`float()` 会抛 `ValueError`——但错误只在运行到该行时才暴露，且没有行号提示（见 E04 只能看到 `could not convert`）。

## 5. 对本期与累计结果的影响

| 现象 | 本期（单次运行）结果 | 累计（跨月）结果 |
| --- | --- | --- |
| 多币种未换算 | 数字被当作同币种相加，本期分摊虚高或虚低 | 每次运行都重新引入同量级误差，且因无币种记录而无从回溯 |
| half-to-even | 单条分摊可能差 1 分 | 大量小额时误差可达数角（F17：0.90） |
| 逐段舍入漂移 | `Σ allocated ≠ cumulative` | 漂移被 `unallocated` 掩盖，`unallocated=0` 不代表无差异 |
| 子分 movement 消失 | 明细缺行，但累计仍计入 | 累计与明细永久性不等 |

## 6. 交接建议（明确标注为实现边界）

以下**不是**当前实现能做的，必须在交接时写清：

1. **精度**：当前为浮点 + `round(...,2)`。若业务要求 Decimal 或指定舍入模式，需改 engine.py:4 与 engine.py:8，并重跑全部 28 个样例以更新 manifest。
2. **币种**：当前无。若需支持，需新增"先换算再累加"的前置步骤，并把币种与汇率写进 allocation 行，否则不可审计。
3. **舍入一致性**：若下游以 `Σ allocated == cumulative` 做对账，当前实现会失败（F17 明确证伪）。对账口径必须先对齐。
