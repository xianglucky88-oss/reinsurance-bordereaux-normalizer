# 05 · 重复文件与月度更正

> rule_version `R-809d7c1.1` · 样例 F10、F18、F19、F03a/F03b、F11a/F11b

## 1. 重复文件：引擎无法识别"同一份文件又提交了一次"

### 1.1 没有文件身份

代码中不存在任何文件级标识：

- `grep -rniw 'file_id|hash|batch|dedup' src/` → 0 命中。
- 输入只有 `losses[]` 与 `treaties[]`，没有文件名、无提交号、无哈希。
- 输出也没有"本次处理了哪些文件"的清单。

因此，**重投一份文件在引擎看来就是"多了几行 loss"**。

### 1.2 证据 F10：单行重复

`C1/M1 = 120` 连续出现两次；层 `L1 = 100 xs 500`。

| 行序 | start | cumulative | L1 分摊 |
| --- | --- | --- | --- |
| 第 1 条 M1 | 0 | 120 | 20 |
| 第 2 条 M1（重复） | 120 | 240 | 120 |

`cumulative_loss = 240.0`。同一个 `claim+movement` 出现两条 allocation 行，**没有任何标记表明其中一条是重复**。

### 1.3 证据 F19：整份文件重投

把 F01 的完整文件原样再拼一遍（M1、M2、M1、M2）：

| 指标 | F01（提交一次） | F19（提交两次） | 变化 |
| --- | --- | --- | --- |
| cumulative_loss | 200.0 | **400.0** | ×2 |
| L2 分摊合计 | 50.0 | **100.0** | ×2 |
| unallocated | 100.0 | **250.0** | +150 |

输出仍然 `status: ok`。**这是交接中最危险的静默错误之一**：累计与层占用被整体翻倍，而系统没有任何异常信号。

### 1.4 为什么"去重"不是加个 if 就能解决

由于引擎没有 `file_id`，可行的去重必须满足以下之一，且都在**引擎之外**：

| 方案 | 在哪实现 | 当前是否具备 |
| --- | --- | --- |
| 按 `(claim, movement)` 唯一键去重 | loader 层 | ❌ 引擎不提供键，且同一键可能合法地出现多次（如分次付款） |
| 按文件哈希 + 提交号登记 | 上游系统 | ❌ 无文件身份字段 |
| 按期间覆盖（本月文件替换上月） | 上游系统 | ❌ 无 `period`/`month` 字段（NI-LOSS-DATE） |

> 结论：**重复文件检测在当前实现中不可达**，必须标为未实现约束，不能写成"系统会自动去重"。

## 2. 月度更正：没有"更正"的概念，只有带符号的数字

### 2.1 更正被降级为"再报一笔负数"

经纪人常见的更正方式是：本月提交一条与原 movement 等额、反号的记录，或以新金额替换旧金额。引擎只看到**带符号的 amount 序列**（engine.py:4）。

- 没有 `corrects_movement`、`supersedes`、`reversal_of` 字段。
- 没有"原 movement 是否已被更正"的状态。
- 不会把更正与被更正项配对；二者只是累计曲线上先后两个点。

### 2.2 证据 F03a/F03b：更正的作用依赖行序

同一组 `+400`、`-100`：

| 行序 | 结果 |
| --- | --- |
| 先 +400 后 -100（F03a） | L1: 300 与 **-100**，两条行 |
| 先 -100 后 +400（F03b） | L1: 仅 **200**，一条行 |

两者累计都是 300，但**明细不同、层占用路径不同**。若更正记录恰好排在原记录之前（例如经纪人按 movement 编号排序而编号不单调），分摊会被改变。

> 更正的正确性因此取决于"更正必须排在被更正项之后"这一**未被代码保证的前提**。

### 2.3 证据 F11a/F11b：本期增量 vs 累计重算

这是月度更正最核心的口径问题。

输入：`M1 = 900`（上月）、`M2 = 200`（本月）；层 `L1 = 1000 xs 100`（区间 [1000,1100]）。

| 提交方式 | cumulative | L1 分摊 |
| --- | --- | --- |
| 全历史（F11a：M1+M2） | 1100 | M2 → **100** |
| 仅当月增量（F11b：只有 M2） | 200 | **无（0）** |

**同一条 M2，在不同的提交口径下，分摊从 100 变成 0。**

原因：引擎的累计从 0 开始（engine.py:4），它不读上月已报的累计。增量文件把 M2 单独当作一个从 0 开始的运行。

### 2.4 影响：本期结果 vs 累计结果

| 口径 | 本期结果 | 累计结果 | 风险 |
| --- | --- | --- | --- |
| 全历史重算 | 每月都重算全部历史 → 本期分摊是该月对历史累计的增量 | 自洽，但需保留全部历史 | 数据量随时间增长；更正月会重述所有后续月份 |
| 当月增量 | 只处理本月行，累计从 0 起 | **与全历史口径不一致** | 层 attachment 判断错误（F11b 的 M2 本应进层却进不了） |

> **交接必须明确声明使用哪一种口径。** 当前引擎只支持"全历史重算"能得到正确的层判断；"当月增量"在层有 attachment 时会产生系统性错误。

### 2.5 更正的可复核样例

| 样例 | 演示 |
| --- | --- |
| F03a / F03b | 同一更正集换序 → 明细不同 |
| F11a / F11b | 同一条 M2 在全历史/增量下分摊 100 vs 0 |
| F19 | 重投整份文件 → 累计翻倍且无告警 |
| F18 | 坏行被静默丢弃，行数无法对账 |

## 3. 对"累计结果"的连带影响

月度更正会**重述历史**，但输出不带任何版本或期间标签（`02` 已证明 allocation 行无版本、无期间）。因此：

- 更正后的累计结果与更正前的结果，**在输出结构上不可区分**。
- 若下游已按上月结果入账，本月更正会改变已入账数字，但没有"这是一次重述"的标记。
- 回滚只能靠**保留输入文件 + rule_version**，重新运行来复现，无法凭输出本身回退。

## 4. 未实现清单

| 能力 | 状态 | 阻塞字段 |
| --- | --- | --- |
| 文件身份与重投识别 | NOT IMPLEMENTED | `file_id` / `statement_no` / `batch_id` |
| 去重键 | NOT IMPLEMENTED | 无稳定唯一键 |
| 更正链接（corrects/supersedes） | NOT IMPLEMENTED | `corrects_movement` / `reversal_of` |
| 期间化累计 | NOT IMPLEMENTED | `period` / `month` / `loss_date` |
| 重述标记 | NOT IMPLEMENTED | 输出无 versions/period |
| 增量口径下的层判断 | NOT IMPLEMENTED | 需传入期初累计，当前不接受 |

## 5. 交接建议

1. **明确口径**：在 SLA/接口文档中写明"每期必须提交全历史，或以外部系统维护期初累计"。当前引擎不能安全地消费纯增量文件。
2. **去重前置**：在 loader 层实现 `(file_hash, claim, movement)` 级登记，并把重复计数写入运行日志；引擎不提供此能力。
3. **更正显式化**：要求经纪人提交更正时携带 `corrects_movement`，由 loader 校验原记录存在且未被重复更正；引擎侧目前只能被动接受带符号数字。
4. **保留证据**：每次运行保存输入文件 + `rule_version` + manifest 哈希，否则重述后无法审计。
